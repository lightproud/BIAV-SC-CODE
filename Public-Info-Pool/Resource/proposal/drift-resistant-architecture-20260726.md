# 抗漂移架构提案 —— 少修一点，多防一点

> 提案人：艾瑞卡（2026-07-26 仓库审视会话）
> 缘起：守密人问「这么多漂移每次手动修复很累，如何在架构设计上更轻松地做到」
> 状态：**提案，待守密人逐项裁定**。本档只提设计，不预设结论。
> 样本来源：本次会话一天内实际检出并修复的 **9 条漂移**（非假想案例）

---

## §1 先看样本：9 条漂移的解剖

一天内检出的全部漂移，按**它当初是怎么产生的**分类（不按严重度）：

| # | 漂移 | 产生机制 |
|---|---|---|
| 1 | `store-patrol` 缺 deploy key，推送被 Ruleset 拒 | 工作流与仓库设置之间有契约，**没有任何地方写着它** |
| 2 | testbed `dream` 用 create-only 语义重写索引 | 测试全开新存储，**「第二天」这个形态不存在于测试** |
| 3 | `loop-support` 地板无矩阵腿，从未复测 | **同一份清单写了两遍**，守卫只查一个方向 |
| 4 | 平台备份读已搬走的路径 | **路径手拼**而非问单一真相源；且从未真跑 |
| 5 | `project-status.md` 写 v0.63.1，实为 0.76.0 | **会变的数字被手抄进档案** |
| 6 | 10 处「git 历史可追」 | **档案断言了一个只有运行时才知道的世界事实** |
| 7 | `todo.md` 两条同号 T60 | **纪律写在文档里，没有机器执行** |
| 8 | 9 条已清行没搬进已清节 | 同上 |
| 9 | 回填的地板数字 85.5 写下时就已过期（实为 87.0） | 同 #5：手抄会变的数字 |

**归纳只有三句话**：

- **同一事实存在两份**（#3 #5 #7 #8 #9）——两份就会分叉，只是时间问题；
- **档案断言了一个不受档案控制的世界**（#1 #6）——世界改了，档案不知道；
- **机制从未真跑过**（#2 #4，以及 #1 的推送腿）——没跑过的东西，绿和坏长得一样。

小学生比喻：抄两遍的电话号码迟早对不上；写在墙上的「隔壁住着张三」在张三搬走那天就成了假话；
从没试过的备用钥匙，和一把配错的钥匙握在手里手感完全相同。

## §2 五招，按「投入产出比」排序

### 招一 · 生成取代对账（最优，漂移变成不可能）

同一事实**只留一处**，其余全部由它生成。银芯已经做对过三次，这条路是走通了的：
`archive_layout.py`（归档布局）· `capability-registry.json`（CI 自动生成）·
CLAUDE.md §5 去枚举化改路由器。

**诚实说明**：本次会话给变异矩阵加的是「两份清单 + 双向对账测试」——那是**次优解**。
最优解是把矩阵**从地板文件生成**：

```yaml
# 现在：两份手写清单 + 一个测试盯着它们
matrix:
  target: [permissions, transport-openai, transport-anthropic, sessions, loop-support]

# 更好：一份清单，矩阵由它派生，第二份根本不存在
matrix:
  target: ${{ fromJSON(needs.targets.outputs.list) }}   # 从 mutation-ratchet.json 读出
```

**候选清单**（凡「会随时间变的数字 / 清单」）：
- 变异矩阵 ← `mutation-ratchet.json`
- `project-status.md` 的版本号与测试数 ← `package.json` + 测试运行产物（改为**生成段**，人只写判断不写数字）
- 各档案里的「N 个工作流 / N 个平台 / N 个概念」类计数 ← 一律指针化或生成

**代价**：生成段与人写段要分开标注，否则人改了会被覆盖。

### 招二 · 台账机器守卫（一次性投入，永久免修）

`todo.md` 的纪律全部是**机器可判定**的，却没有一行代码在判：ID 唯一、编号不重用、
状态字段取值合法、已清行必须在已清节、每条必须有源出处指针。#7 #8 两条漂移属于此类，
写一个 `tests/test_todo_ledger.py`（约 100 行）即永久消除。

同类可守：`decisions.md`「覆盖」列指向的条目必须存在；`lessons-learned.md` 编号不重用。

小学生比喻：班规贴在墙上没人念，就等于没有；把它做成教室门口的转闸机，违规的人自己过不去。

### 招三 · 死手开关（治「哑掉」这一类，本次会话最痛的一条）

今天最贵的教训不是巡检器坏了，而是**巡检器坏了七天没人知道**——因为发现坏的责任落在
巡检器自己身上。任何「靠自己喊坏」的机制，坏的时候恰好是它喊不出来的时候。

**设计**：每个定时机制每轮必须往一个共享心跳台账写一行（谁 / 何时 / 产物指纹）。
另设一个**只看缺席、不看内容**的极简检查：某机制 N 天无心跳即红。关键是这个检查要
**足够蠢、足够独立**——它不理解任何业务，只会数日子。

现成基础：testbed 的 `ci-status` 巡检器已经在做类似的事（今天它确实报出了两条红），
差的正是「**当巡检器自己缺席时谁来报**」这一层。

小学生比喻：值班表要求每人签到；查岗的人不需要懂业务，只要看见空格就报警——包括查岗
的人自己那一格。

### 招四 · 把档案断言变成可执行断言

CLAUDE.md 的路径引用测试**今天真的接住了艾瑞卡**（§6.3 初稿写了已死路径 `data/db`，
测试当场转红）。这个模式该扩大：凡档案里断言了一个**外部世界事实**，就该有一条可执行检查。

**做法**：给这类断言一个显式登记表（断言类型 + 参数 + 出处），一个 checker 全跑一遍：

| 断言类型 | 例子 | 检查方式 |
|---|---|---|
| `path_exists` | 「见 `scripts/foo.py`」 | 已有，继续 |
| `ref_exists` | 「回滚保险分支在」 | `git ls-remote` |
| `release_exists` | 「二进制在 unpacked-assets 桶」 | Releases API |
| `workflow_secret` | 「本工作流需 BOT_DEPLOY_KEY」 | 静态扫 yaml，缺即红（可治 #1）|

#6 的十处措辞若当初是登记过的断言，备份分支被删的**当天**就会红，而不是六天后靠人肉发现。

### 招五 · 首跑实证纪律（今日已点头生效）

已落 `memory/methodology.md`「首跑实证纪律」节：新增定时机制当天必须 dispatch 实证，
未真跑不得记「已落地」；实证以**产物**为准而非 `conclusion=success`（空跑也绿）。

## §3 一条元规则（免得守卫自己变成新债）

> **守卫必须比它守的东西简单。**

否则只是把漂移搬了个家——守卫自己会腐坏、会误报、会被人加 skip 绕过。判据三条：
① 守卫失败时，错误信息本身要说清怎么修（今天新加的矩阵测试即照此写）；
② 守卫不得需要外部凭据或网络才能跑（招四的 `ref_exists` 类要能在无网时优雅跳过）；
③ 守卫代码量应显著小于被守对象。

## §4 建议实施顺序

| 序 | 招 | 投入 | 一次性消除的漂移类 |
|---|---|---|---|
| 1 | 台账机器守卫（招二）| 小（~100 行测试）| #7 #8 类，永久 |
| 2 | 矩阵改生成（招一，先做一个样板）| 小 | #3 类，并给招一立范例 |
| 3 | 状态档版本数字改生成（招一）| 中 | #5 #9 类 |
| 4 | 死手开关（招三）| 中 | 「哑掉」类——本次最痛 |
| 5 | 断言登记 + checker（招四）| 中偏大 | #1 #6 类 |

**不建议做的**：不要为「档案措辞风格」写守卫（易误报、价值低）；不要在守卫里塞业务判断
（招三蠢一点反而更可靠）。

## §5 一句话回答守密人的问题

漂移不是勤奋能解决的问题，**手动修复的次数只是漂移速率的函数**。要真正省力，只有三个动作：
**让第二份副本不存在**（生成）、**让纪律自己拦人**（机器守卫）、**让沉默本身触发告警**（死手开关）。
今天修的九条，若这三样到位，其中七条根本不会发生。
