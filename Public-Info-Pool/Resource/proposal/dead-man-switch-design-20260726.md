# 死手开关设计 —— 让沉默本身触发告警

> 设计人：艾瑞卡（2026-07-26 仓库审视会话）
> 依据：守密人 2026-07-26 裁定「先出设计再施工」（抗漂移提案招三）
> 状态：**设计稿，待守密人过目后再施工**。本档不含实现。
> 上游：`Public-Info-Pool/Resource/proposal/drift-resistant-architecture-20260726.md` §2 招三

---

## §1 要解决的到底是什么

2026-07-26 最贵的一条教训不是「巡检器坏了」，而是**巡检器坏了七天没人知道**——因为
发现它坏的责任落在它自己身上。同日另一条更极端：`community-platform-backup.yml`
建成次日即坏，但它**从未触发过**，连「坏了」这个事件都还没发生。

两者合起来定义了本设计的靶：

> **不是「机制报错时告诉我」，而是「机制该出声却没出声时告诉我」。**

前者已有（工作流失败会红）；后者当前**全仓为零**。

小学生比喻：教室点名能查出「谁回答错了」，查不出「谁根本没来」——而缺席恰恰是更严重的
那种。死手开关就是那本点名册：它不听课，只数空座位。

## §2 现状盘点（硬数字）

- 工作流总数 **42**，其中带 cron 的 **24 个**（25 条 cron 表达式，`discord-archive.yml` 有两条）；

  今天它确实报出了两条红，说明思路对——**但它自己就是哑掉七天的那个**；
- 覆盖缺口：24 个定时工作流中，有 **14 个不在任何监控名单里**；
- 告警通道：银芯目前无推送通道（挂账 T34），告警只能落仓内 + 会话可读。

## §3 设计选择（每条都给取舍理由）

### 选择一：拉模式，不是推模式 —— **拉**

| | 推（每个工作流写心跳）| 拉（一个作业查 Actions API）|
|---|---|---|
| 改动面 | 要动 24 个工作流 | 只加 1 个作业 |
| 漏网 | 新工作流忘了加心跳 = 静默漏 | 自动覆盖全部 |
| 可信度 | 心跳可能在真活干完之前就写了 | 只认 `conclusion: success` |

**取拉模式**。理由是漏网面：推模式要求每个新工作流的作者记得加一步——这正是今天出问题的
那类「靠人记得」的约定。

### 选择二：阈值从 cron 自己推导，**不建第二份清单**

监控名单与期望节拍**全部由工作流文件生成**：解析每个 `.yml` 的 cron，算出期望间隔，
阈值取 `期望间隔 × 2 + 宽限`。这直接套用提案招一——**清单只有一份，就是工作流自己**。

- 每 3 小时的（`update-news`）→ 阈值 ~7 小时；
- 每日的（`store-patrol`）→ ~2 天；
- 每周的（`sdk-mutation-ratchet`）→ ~15 天；
- 每月的（`community-platform-backup`）→ ~62 天。

**只有 `workflow_dispatch` 没有 cron 的不纳入**——它们本就不该定期出声。

### 选择三：判「缺席」，也判「从未」

两种沉默要分开报，因为病因不同：

- **`STALE`**：曾经成功过，但最近一次成功超出阈值（今天的 store-patrol）；
- **`NEVER`**：从来没有过一次成功（今天的 community-platform-backup）——
  这条同时兜住「首跑实证纪律」的漏网者。

### 选择四：谁看守卫自己 —— 双人互看 + 人是最终死手

这是本设计最难的一环，诚实说明：**任何自动守卫都可能自己哑掉**，不存在纯技术闭环。
三层，越往下越笨、越可靠：

1. **两个不同宿主互看**：死手检查跑在与 testbed 巡检**不同的工作流**里，二者互列对方为
   监控对象——一个哑了，另一个报；
2. **状态落成仓内单文件**（如 `Public-Info-Pool/Record/heartbeat/status.json`，含
   `generated_at`），会话开场一眼能看出「这份状态本身有多旧」；
3. **人是最终死手**：月检档加一句「看 status.json 的 `generated_at`」。守密人偶尔一瞥，
   就是最后那道不会哑的开关。

小学生比喻：两个守夜人各自记录对方有没有打瞌睡；再在门口挂一块写着「上次巡查时间」的
牌子——牌子上的时间要是停在上个月，路过的人自己就看出来了。

### 选择五：告警落哪 —— 提交 + 巡检报告，不新建通道

无推送通道（T34），故：状态文件提交进仓（`[skip ci]`），并让 testbed 巡检器把它读进
每日报告。**不为本设计新建通知通道**——那是 T34 的事，不在此处顺手扩张。

## §4 误报控制（守卫的信誉是一次性的）

守卫喊狼来了三次以后就没人看了。四条克制：

1. **禁用的工作流跳过**（GitHub 会自动禁用长期无活动仓库的 cron，这是真实误报源）；
2. **阈值给足**（×2 + 宽限）：GitHub 的定时触发本就会延迟数十分钟，卡太紧必然假红；
3. **NEVER 类给宽限期**：新建工作流在其首个 cron 到期前不报（否则每加一个新工作流就红一次）；
4. **只报状态、不猜原因**：死手开关不许分析「为什么没跑」——它一分析就会变复杂，
   而元规则要求**守卫必须比它守的东西简单**。

## §5 施工范围（守密人点头后）

| 件 | 内容 | 量级 |
|---|---|---|
| 检查脚本 | 解析 cron → 算阈值 → 查 Actions API → 产 status.json | ~150 行 |
| 工作流 | 每日跑一次，提交状态文件；与 testbed 巡检互列监控 | ~40 行 |
| 测试 | cron 解析与阈值推导的单测（含跨月 / `*/3` / 多 cron）+ 状态文件 schema | ~80 行 |
| 文档 | `methodology.md` 月检档加「看 generated_at」一句 | 1 行 |

**不做**：不做趋势图、不做原因分析、不做自动修复、不接推送通道。

---

## §6 待守密人裁定的三点

1. **阈值系数**：建议 ×2 + 宽限；是否接受（更紧＝更早发现、更多假红）？
2. **NEVER 类宽限**：新工作流首个 cron 到期后多久开始报——建议「首个 cron 到期 + 1 个周期」；
3. **互看关系**：死手检查与 testbed 巡检互列，还是死手只单向看所有人（含 testbed）、
   自身仅靠 status.json 的 `generated_at` + 人眼？后者更简单，但少一层自动兜底。

---

## §7 一句话

死手开关不是又一个监控系统，它只干一件事：**数空座位**。它必须蠢到不会坏，
以及在它真的坏掉那天，牌子上停摆的时间戳会替它说话。
