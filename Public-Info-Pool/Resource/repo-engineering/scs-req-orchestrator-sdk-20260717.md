## §1 定位声明

**银芯编排 SDK 持有分子:钟、跨会话状态、会话装配。它把"活得比一次调用久"的 agent 所需的脏活——循环、调度、重试、恢复、台账——做成可复用零件,交给宿主装配。**

三条硬性质:

1. **库,不是框架。** 宿主持有 main()。每件零件可单独拿取、自由组合、整箱不要;不存在"必须长成编排 SDK 要求的形状"的宿主。
2. **对代理 SDK 无特权通道。** 编排 SDK 能做到的一切,宿主徒手用代理 SDK 公开接口(R1–R5)也必须能做到。它是糖,不是门。哪天它被迫伸进引擎内部才能实现某功能,暴露的是 R1–R5 漏缝——回头修代理侧需求档,不给编排开后门。
3. **数据面在 SDK,渲染在宿主。** 一切对人的呈现(通知送达、界面显示)只定契约缝,实现由宿主注入。

与代理 SDK 的分界一句话:**代理持有原子(一次结构化调用,含 query 内子代理),编排持有分子(跨调用的钟与状态)。** 判别式:节点要活得比父调用久、或要等墙钟/外部事件 → 编排;否则 → 代理引擎内。

> **判别式补维注(守密人 2026-07-26 裁定,产品审视 P5 回填)**:上述两项判据**漏了一维**,
> 现补第三项——**或由 agent 侧主动发起、需在台账留审计的对外动作(触发权)→ 编排**。
> 补的理由是规则与现实不一致时先确认哪个错了:`createDeliveryChannel`(§5 送达契约)
> **不满足**原判别式任何一项(实测 `clock.now()` 四处全为打时间戳、`setTimeout` 零处,
> 源码自陈「executes inline by spec」),但 §3 场景分拣一直把它归编排、理由写的是
> 「编排(触发权)+ 宿主(送达面)」。**即判据表述漏了 §3 已在用的那一维,不是 delivery
> 放错了地方**。守密人裁定:维持 delivery 在编排包内,补齐判别式表述。
> 「触发权」的边界:**发起权与审计在编排,呈递实现在宿主**(硬性质③不变)。

> **归属边界的诚实标注(同批裁定)**:delivery 当前**无生产消费方**(产品审视 P2 实测:
> 全仓零真实调用点),故它虽归属正当,成熟度未经真实使用检验——见 §6 的「已验证」标尺。

## §3 场景分拣(六场景 → 能力面)

| 场景 | 归属 | 编排侧能力 |
|---|---|---|
| 动态子代理派发 | **代理 SDK 引擎内**(Task 嵌套,已有) | 不进编排包 |
| 后台任务追踪 | 编排 | 任务台账(§4,首战) |
| loop / 机械脚本历程 | 编排 | loop 骨架:周期轮询+预算帽+跨重启恢复,长在台账上。**覆盖注(守密人 2026-07-29 裁定 D8,设计第三轮)**:「loop 骨架」= 组合谱系文档(`docs/ASSEMBLY.md`,Scheduler+LedgerDriver+AgentExecutor 组合即 loop),**不建同名模块**——两个已验证消费方均徒手组合成 loop,骨架模块落地首日即零消费方(P2 判词)且持装配意见即违硬性质① |
| 跨会话目标循环 | 编排 | goal 追逐器:引擎 goal 管一次 query 内达标,跨 query 重发起归此;记账为多 session,goal 语义留场景层 |
| agent 发起对话 | 编排(触发权)+ 宿主(送达面) | §5 送达契约 |
| workflow 工具流 | 编排 | 声明式图执行器;图定义是数据,放能力内容热层,改流程零部署 |

## §4 任务台账(首战能力面)

公共底座,其余零件长在它上面。

- **层级:session → query 两级。** session 为派发单位、携业务意图;query 为执行记录,每轮/每次重试一条。goal 不入表(场景层语义,如需串联由场景自理)。
- **状态机:SDK 定死封闭状态集**(pending / running / retrying / failed / done 一类,实现时定稿),语义统一,挂 session 级;query 级只记轮次结果。重试 = session 处 retrying、新 query 记录追加,与两级结构自洽。
  > **状态集定稿(2026-07-18 施工回填,授权见施工封面 §2;2026-07-22 P0-D1 扩容回填,
  > 授权见守密人同日「先修封闭状态集」指令)**:session 级封闭集 =
  > `pending | running | retrying | failed | done | cancelled`(terminal =
  > done / failed / cancelled;事件集 `claim | attempt:ok | attempt:error |
  > attempt:timeout | cancel`,重试复用 claim 事件,cancel 自三个非终态皆可入、
  > 落 cancelled 终态且永不自动重跑);query 级轮次结果 = `ok | error | timeout |
  > cancelled`(cancelled 仅由 `cancelSession` 落账,executor 不可上报)。
  > 裁定记录见 `memory/decisions.md` 2026-07-18「编排 SDK 第一战」条;cancelled
  > 终局语义源出 BPT 需求 P0-D1(2026-07-22),实现随 0.76.0 落地。
- **存储:只定接口,实现全由宿主注入。** BPT 注入服务端 DB(五层架构第四层,本就是有状态重点守护区)。SDK 自身无状态、不带电池。
- **驱动器:SDK 提供活组件。** 宿主启动后由它持钟自动调度重试/超时,推动状态流转;生杀权在宿主(启动/停止即宿主的裁量)。
- 查询面跨场景通用(封闭状态集是前提):在跑什么、挂了什么、挂在哪,一套查询通吃五场景。

## §5 agent 发起对话:送达契约

- **SDK 只定一个送达接口,实现全由宿主注入**(飞书 webhook、客户端推送等宿主自接)。与台账存储同构:契约缝在 SDK,电池在宿主。
- **发起动作同时落台账一条审计记录**;送达走注入接口保即时性,不依赖轮询。
- 拒绝方案与理由存档:内置事件总线(SDK 长出消息设施,与宿主已有通道重复);台账特殊任务类型+轮询(告警即时性不达标)。

## §6 例程(活体证明)

`examples/` 至少三份,每份**只准 import 两包公开面**——例程写不出来 = 接口面漏缝,与代理侧 §7.1 装配测试同构,是"无特权通道"性质的可运行证明:

1. 最小 loop:周期轮询 + 预算帽 + 到帽收尾(消费代理侧 R2 事件流)
2. schedule:定点触发 + 错过补偿 + 跨重启恢复
3. workflow 图:声明式定义派发多 worker + 收敛合入

> **「已交付」vs「已验证」两级标尺(守密人 2026-07-26 裁定,产品审视 P2 回填)**
>
> 本节原标尺——「例程写不出来 = 接口面漏缝」——检验的是**可行性**(接口面够不够用),
> **不是需求**(有没有人要)。一个只服务于自己例程的模块永远能通过它。产品审视实测:
> 六族里 `goal` / `delivery` / `workflow 声明式加载` 在**全仓零真实调用点**,
> `WorkflowRun` 仅 1 处且是自家 demo;而 `ledger` / `driver` / `scheduler` 有两个
> 互不相干的真实消费方(生产商店巡检 + 试金石 daemon)。
>
> 故分两级,**原标尺保留为第一级**:
>
> - **已交付**:例程只 import 两包公开面即可写出来(原标尺,证明接口面无漏缝);
> - **已验证**:存在**至少一个不是为演示它而写的消费方**——该消费方有自己的业务目的,
>   台账是被它「拿去用」的。`store-patrol` 与 testbed `daemon` 是这样的消费方;
>   `workflow-fanout.mjs` 不是(它存在的目的就是演示 workflow)。
>
> **仅「已交付」的能力面须在 README / CONTEXT 明标「实验面,无生产消费方」**,
> 免得读者把六族齐全误读成六族都经真实使用打磨。标注不等于弃用:代码保留、测试保留、
> 变异地板保留;真实需求出现即可升级为「已验证」并去标。
