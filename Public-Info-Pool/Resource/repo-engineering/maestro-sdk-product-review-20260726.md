## §0 总评：一个被证明「造得出」、但只有一半被证明「有人要」的产品

先记正面账，且这笔账是硬的：

**宪章 §8 的验收标尺是「新场景首发——挑一个新循环任务（商店巡检类）直接长在台账+驱动器上」。
这条真的达成了。** 商店巡检每日 CI 生产在跑，台账文件里 4 条会话全 `done`、attempts 均为 1，
跨重启恢复与幂等派发键都在真实生效；试金石 `daemon.mjs` 是**第二个独立消费方**，同样长在
ledger + driver + scheduler 上。**一个能被两个互不相干的消费方复用的任务台账，这是真价值。**

然后是本轮的核心判断：**六个模块族里，三族（goal / delivery / workflow 声明式加载）在整个仓库内
零真实调用点**。它们不是写得差——恰恰相反，写得和被消费的那三族一样讲究——而是**供给建在猜测上**。
宪章 §6 把验收标尺定为「例程写不出来 = 接口面漏缝」，那是**可行性检验**；家族对「能不能造出来」
有极严格的证明（67 项审计 / 400 单测 / 六靶变异棘轮），对「有没有人要」在这三族上**没有任何证明**。

小学生比喻：厨房练出了六道菜的手艺，每道都能做得很规整；但客人这半年只点过三道，
另外三道的食材天天还在采买、天天还要检查新鲜度。手艺没问题，问题是备货按六道菜备。

## §1 P1【高】`peerDependency` 无代码支撑，且与硬性质①直接冲突

### 现状核实

`package.json` 声明：

```json
"peerDependencies": { "silver-core-agent-sdk": ">=0.71.0 <1.0.0" }
```

而 **maestro 的 `src/` 对代理 SDK 零 import**。全量扫描 `src/` 只命中两处，都是**注释散文**：
`driver.ts:30`（「typically wrapping a silver-core-agent-sdk query() call」）与
`index.ts:12`（硬性质②的表述）。没有任何一行可执行代码引用它。

宪章 §2 给的理由是「编排的 peerDependency 声明兼容的代理版本区间，**消费代理侧 R6 版本声明面**」——
但它并不消费 R6 的任何东西。**这是一条按理由写下、而该理由从未落成代码的依赖声明。**

### 为什么这是产品问题而不是洁癖

三点叠起来才成立：

1. **npm 7+ 默认自动装 peer 依赖**。声明一条 peer 就等于要求每个消费方装一个本库从不使用的包。
2. **它与硬性质①正面冲突**。硬性质①原文：「每件零件可单独拿取、自由组合、**整箱不要**」。
   而 `examples/store-patrol.mjs` 自己的注释是最好的反证——「the agent SDK is **not needed** here
   — the executor is plain HTTP; the ledger/driver are **agent-agnostic by design**, hard property §1.1」。
   **例程亲口说了台账与代理无关，package.json 却要求装代理。**
3. **它挡掉一类真实用户**：只想要「一个能跨重启恢复的任务台账 + 持钟驱动器」的宿主
   （商店巡检就是这种宿主，它的 executor 是裸 HTTP），当前必须连带装一个 1.6MB 的代理 SDK。

三条修法（选哪条是裁定）：**甲** 删掉该 peer 声明（最诚实：代码不用就不声明）·
**乙** 改为 `peerDependenciesMeta: { optional: true }`（保留版本区间的信息价值、不强制安装）·
**丙** 真去消费 R6 版本声明面（让理由落地，但要先想清楚消费它做什么）。

小学生比喻：说明书写着「本器材须配 A 牌电池」，可拆开一看它根本不用电池——
买的人还是得先去买一盒电池才让你装。

## §2 P2【高】六族里三族零消费者：2,521 行在维护一个还没有的需求

### 现状核实（真调用点计数，排除注释与本包自身测试）

| 模块族 | 包外真实调用点 | 判定 |
|---|---|---|
| `TaskLedger` | testbed `daemon`/`baseline`/`store-contract` + 5 个例程（**含生产 store-patrol**）| **有效性已证** |
| `LedgerDriver` | testbed `daemon`/`store-contract` + 4 个例程 | **有效性已证** |
| `Scheduler` | testbed `daemon` + 2 个例程 | **有效性已证** |
| `WorkflowRun` | **1 处，且是自家 demo**（`examples/workflow-fanout.mjs:108`）| 需求未证 |
| `GoalChaser` | **0**（无例程、无 testbed、无生产）| **需求零证** |
| `createDeliveryChannel` | **0** | **需求零证** |
| `loadWorkflowGraphFile` / `parseWorkflowGraphSource` | **0** | **需求零证** |
| `purgeSession`（今日新加，诚实标注）| **0**（例程里只有一句注释提到它）| 新面，未及消费 |

零消费面的规模：**src 836 行 + 测试 1,685 行 = 2,521 行**。

### 这些面并非「低成本挂着」

三条实际成本，逐条可核：

1. **周检算力一半花在零消费者身上**。变异棘轮六靶里，`goal-decision`（地板 100）、
   `delivery-channel`（100）、`workflow-load`（98.04）**三靶都在零消费模块上**——
   六分之三的周检预算，守着没人调用的代码。
2. **每次全局改动都要顺带改它们**。今日 F1 修复就是实例：`GoalChaser` 的终态判定、
   `GoalAction` 的新成员、`graphStatus` 的语义——全部为一个零消费者的模块做了设计裁定与回归锁。
3. **它们参与了「产品看起来很完整」的错觉**。README 现在列六族齐全，读者会以为六族都经过真实使用打磨；
   实际只有三族有消费方反馈过。

### 宪章自己的验收标尺不足以覆盖这件事

§6 原文：「`examples/` 至少三份，每份只准 import 两包公开面——**例程写不出来 = 接口面漏缝**」。
这条标尺很好，但它检验的是**可行性**（API 够不够用），不是**需求**（有没有人要）。
一个只服务于自己例程的模块，永远能通过这条标尺。

**建议的补充标尺（可复用）**：一族能力从「已交付」升为「**已验证**」，须有**至少一个不是为演示它而写的
消费方**。store-patrol 与 testbed daemon 是这样的消费方（它们各有自己的业务目的，台账是被拿去用的）；
`workflow-fanout.mjs` 不是（它存在的目的就是演示 workflow）。

小学生比喻：作业本上六道题都写了、都验算过了；但只有三道题是老师真出过的，
另外三道是自己出给自己做的——验算再仔细，也证明不了那三道题会考。

## §3 P3【中】零内置电池：把同一段易错代码转嫁给每个消费方

### 现状核实

两个真实消费方各自手写文件型 `LedgerStore`：

| 消费方 | 有效行 |
|---|---|
| `examples/store-patrol.mjs` `fileLedgerStore` | 43 |
| `projects/silver-core-testbed/src/store.mjs` | 38 |

**逐行相似度 86%**（`difflib.SequenceMatcher` 实测，已剥注释空行）。两份代码在做同一件事：
读一个 JSON、Map 存会话、数组存 query、写时全量落盘。

全仓 `async putSession` 实现共 **31 处**——其中 29 处是本包测试夹具（**这是正当的**：
r5 性质测试刻意造 plain / CAS / 故障注入等多种 store 变体，那是测试的本职），
真实消费方是 2 处。

### 为什么值得一议

宪章 §7 列「**不内置存储实现**」为非目标，这个方向是对的——不想把消费方绑在某个数据库上。
但「不内置**实现**」不等于「不提供**一个可选参考实现**」。当前形态的实际后果是：

- 每个消费方都要重写同一段**契约关键**代码（写错了，幂等 / 跨重启恢复 / 租约就全不成立）；
- SDK 对这件事给出的答案是**一套 12+4 检查的契约套件，用来检查你抄得对不对**——
  **契约套件的存在本身就是承认这活容易写错**；
- 而它没提供那份「抄什么」。README 里 `LedgerStore` 只出现一次，且是在一句能力罗列里。

三条修法（选哪条是裁定）：**甲** 发一个可选子路径导出的内存 store + 文件 store 参考实现，
明标「参考实现，生产请评估」（不违反 §7 的精神——不内置**默认**，但给一个可拿的）·
**乙** 不发实现，但把契约写成一份文档 + 一份可复制的 50 行样板（成本最低）·
**丙** 维持现状（两个消费方各写一遍，第三个再写一遍）。

小学生比喻：老师说「保温杯自己带，学校不发」——方向没错。
但每个学生带来的杯子都得通过同一套 16 项漏水检查，学校却不肯给一张「合格杯子长什么样」的图纸。

## §4 P4【中】文档面与「要求宿主装配」的定位严重不匹配

### 现状核实

| | agent SDK | maestro SDK |
|---|---|---|
| `docs/` 文件数 | **12**（ARCHITECTURE / COMPAT / CONCURRENCY / ERRORS / MEMORY / MIGRATION ×2 / ONBOARDING / OPENAI-PROTOCOL / PERFORMANCE / POSITIONING / MEMORY-GOVERNANCE）| **0（无 docs/ 目录）** |
| `docs/` 总行 | 3,918 | 0 |
| README 行 | 293 | **72** |

而 maestro 那 72 行里，**28 行是本会话一小时前才加的**（本轮上一个 PR 补的「宿主必须自己决定的三件事」；
改动前为 44 行）。也就是说：截至今天上午，这个产品面向消费方的全部文档是 **44 行 README**。

### 为什么这一条比看起来严重

这是一个**要求宿主注入存储、注入送达 sink、注入 evaluator、自己持 main()、自己决定并发上限与保留策略**的库。
**它的采纳门槛几乎全在文档上**——代码本身的注释极好（每条防御带审计轮次溯源），
但那是给**维护者**看的，不是给**消费方**看的：消费方读不到 `src/`，他读 README。

而且 maestro 恰恰是家族里**更需要**这些文档的那一个：它的并发模型比代理侧复杂——
per-session 互斥 + 可选 CAS 围栏 + 认领租约 + 六态状态机（三个终态语义各不相同）+
「settle-then-append 提交点」+「哪些 id 本身就是簿记」。代理侧有 `CONCURRENCY.md` 讲这些，
maestro 一份都没有。

**最小可行补法**（不必对齐 12 份）：三份就够——`ONBOARDING.md`（30 分钟接上一个循环任务，含 store 样板，
呼应 P3 乙案）· `CONCURRENCY.md`（互斥 / CAS / 租约 / 终态语义 / 提交点，本包最需要）·
`OPERATIONS.md`（并发上限 / 保留策略 / 中止 / 「id 即簿记」的运维反作用，把本会话 README 那 28 行扩开）。

小学生比喻：卖的是一套需要自己组装的家具，螺丝分类做得极细致、每包上都写着「此螺丝为何是这个型号」——
可就是没有装配说明书，只有一张 44 行的包装清单。

## §5 P5【中】`delivery` 不满足宪章自己的归属判别式

### 现状核实

宪章 §1 判别式原文：**「节点要活得比父调用久、或要等墙钟 / 外部事件 → 编排；否则 → 代理引擎内。」**

`createDeliveryChannel` 对钟的使用（全量扫描 `src/delivery/channel.ts`）：`clock.now()` 四处，
**全部只为打时间戳**；`setTimeout` **零处**，不等待、不轮询、不跨调用存活。
其源码注释自陈：「This is the one component that **executes inline by spec**.」

也就是说：它既**不**活得比父调用久，也**不**等墙钟或外部事件。**按宪章自己的判别式，它不是分子。**

宪章 §3 把它归编排的理由是「编排（触发权）+ 宿主（送达面）」——但「触发权」并不是判别式里的项，
而它实际做的事（写一条审计会话 + 直接调 sink）用代理侧公开面徒手也能写，
正是硬性质②所说的「它是糖，不是门」。

### 与 P2 叠加后的结论

`delivery` 同时是：**零消费者**（§2）+ **不满足归属判据**（本节）。**在需求与归属两条线上都是最弱的一块面。**

必须说清楚：**它写得不差**——审计先行（落账失败不发信）、sink 失败入回执不上抛、
租约竞态吞得干净，都是好设计。问题不是质量，是**它可能不该在这个包里**。

三条处置（选哪条是裁定）：**甲** 维持（承认判别式有例外，并把「触发权」补进判别式，让规则与现实一致）·
**乙** 移出（送达契约下沉代理侧或独立第三包，maestro 收敛为「钟 + 跨会话状态」的纯分子包）·
**丙** 冻结（保留不删、README 标「实验面，无生产消费方」，等真实需求出现再定）。

小学生比喻：乐队指挥的活儿是「打拍子、管进出场」；而这块面干的是「演出结束后去前台递一张节目单」——
递得很得体，但那不是指挥的活儿，规则里也没写指挥该干这个。

## §6 P6【低 · 记账 + 事后证实守密人裁定】锁步的真实代价，与其正当性

### 现状核实

锁步纪元（0.68.0 起，守密人 2026-07-18 裁定）：

| | 版本条目数 | 其中「本包零改动」纯空转 | 空转占比 |
|---|---|---|---|
| agent SDK | 18 | **4**（0.73.0 / 0.74.0 / 0.76.0 / 0.78.0）| **22%** |
| maestro SDK | 16 | **6**（0.70.1 / 0.71.1 / 0.71.2 / 0.72.1 / 0.75.0 / 0.77.0）| **38%** |

代价是真实的：两侧消费者看到的版本号里各有两三成是「与你无关，但请重新 pin」。
对 agent SDK 尤其具体——它有真实的生产消费方（BPT 按 `npm pack` tarball 版本 pin），
每个空转版本都是一次无内容的重新 pin 决策。

### 但同一份数据反证了宪章的原理由

宪章 §2 原文主张独立时钟，理由是「**代理慢（商品泵），编排快（跟宿主需求）**」。
实测：锁步纪元里 **agent 18 版 / maestro 16 版——编排并不比代理快，还略慢。**

**独立时钟的立论前提是假的。** 守密人 2026-07-18 的锁步裁定因此站得住：
用两三成空转版本号，换来「哪个 agent 配哪个 maestro」这个问题永远不用查——
对一个单维护者的两包家族，这笔交易是合算的。

**本条不是问题，是把已付代价记上账，并对裁定做一次事后证实。** 唯一的可选改进：
空转侧的 CHANGELOG 条目已经写了「本包零代码改动」（本会话新增的 0.78.0 就是这么写的），
建议把这行**格式固定**成机器可识别的一句，将来可自动生成「对你有实质变更的版本」清单给消费方。

小学生比喻：兄弟俩的衣服永远买同号——有时其中一个根本没长个也得换新的。
浪费是真的，但从此再没人搞错「哪件配哪件」，而且实测两人长得一样快，本来就没必要分开买。

## §7 汇总：产品面记分卡

| 维度 | 判定 | 依据 |
|---|---|---|
| **定位是否清楚** | ✅ 清楚 | 「持有分子：钟 / 跨会话状态 / 会话装配」+ 一句话判别式，比多数库讲得明白 |
| **三条硬性质是否守住** | ⚠ 两守一破 | ①「零件可单独拿取」被 peerDep 破（P1）· ② 无特权通道守住（src 零 agent import）· ③ 数据面/渲染分离守住 |
| **归属判据是否自洽** | ⚠ 一处例外 | `delivery` 不满足自己的判别式（P5）|
| **有效性是否已证** | ⚠ 半数 | ledger / driver / scheduler **已证**（两个独立生产消费方）· workflow / goal / delivery **未证**（P2）|
| **采纳成本是否合理** | ✗ 偏高 | 每消费方手写 ~40 行契约关键 store（相似度 86%）+ 文档 0 份（P3 / P4）|
| **版本策略** | ✅ 合理（代价已记账）| 锁步裁定被数据证实；空转两三成（P6）|
| **工程质量** | ✅ 高于本仓平均 | 上一轮审视结论，四缝已修，400 单测 / 六靶棘轮 |

**一句话**：**工程质量与定位表述都在水准之上；产品面的短板不在做得好不好，而在两件事——
供给超前于需求（三族零消费者），以及采纳门槛（文档与 store 样板）几乎没建。**
