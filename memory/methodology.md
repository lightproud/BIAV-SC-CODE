# 核心方法论

> 最后更新：2026-06-28 by 艾瑞卡（全仓 md 矛盾审计同步：多会话模型退役横幅 / 分支政策放宽 / 报告流程数据根与落点更新）；上次 2026-05-29 新增银芯报告生产流程节
>
> 以下六条是制作人 Light 在实践中提炼的 AI 协作方法论，是整个 brain-in-a-vat 项目的思想基础。

1. **发现 AI 的综合智能**：Claude 不只是写代码或回答问题的工具，它具备判断、分析、审美、策划等综合能力，可以作为制作人级别的协作伙伴。

2. **发现 Code 的自主执行能力**：Claude Code 能独立写代码、自我纠错、完成工程任务，不需要人类逐行指导。

3. **数据本身是金矿**：有了结构化的数据体系，AI 可以自动生成知识文档、wiki 页面、分析报告。数据的价值不在于存储，在于被 AI 理解和加工。

4. **知识传承体系让 AI 持续变强**：通过仓库中的 memory/ 目录建立共享知识库，每个新会话不从零开始，而是站在所有前辈会话的肩膀上。知识不会因会话结束而丢失。

5. **AI 能自我驱动**：AI 可以主动采集外部信息（社区动态、wiki 数据）并沉淀为内部知识（JSON 数据库、分析报告）。人类只需设定方向，不需要手动喂数据。

6. **多 AI 协作是可行的**：通过仓库作为共享大脑、Issue 作为任务协议、角色分工（Chat 思考 / Actions 执行 / Code 探索），多个 AI 实例可以像团队一样协作，各司其职。

## 核心架构：双集群 + 人类调度器

```
制作人（Light）= 唯一调度器
├── Chat 集群（随开随用，无固定数量）
│   ├── 某次聊战略方向
│   ├── 某次审视仓库
│   ├── 某次研究游戏机制
│   └── ...
└── Code 集群（按子项目固定）
    ├── 主控制台 — 协调、架构决策、代码审查（不写业务代码）
    ├── Code-site — 主站导航页 + 部署流水线 + 跨站视觉一致性
    ├── Code-wiki — 游戏数据集 + Wiki 站点
    ├── Code-news — 新闻聚合 + 报告系统
    └── Code-game — 衍生游戏（规划中）
```

### Chat 集群
- **无状态**：用完即走，不保留固定会话
- **无层级**：不需要一个 Chat 管其他 Chat，人类自己就是调度器
- **通过仓库传递记忆**：产出（任务清单、分析报告等）交给 Code 主控台执行
- 可以同时开多个，各干各的

### Code 集群
- **有状态**：按子项目分工，每个子项目一个会话
- **全部直接推 main**：不使用 feature 分支，冲突时 `git pull` 后重试
- **同一子项目不要同时开两个 Code 会话**，避免冲突
- 主控制台负责协调和架构决策，不写业务代码
- **按业务分会话，不按技术层分会话**：前后端任务切换是子项目内部的正常节奏

### 两个集群的连接
- 仓库是中间层（共享外脑）
- `memory/` 目录是跨会话的结构化记忆
- Chat 读仓库获取上下文，产出决策 → Code 执行决策写回仓库
- **Chat 的数据访问方式**：Chat 通过 GitHub API 读仓库文件，不能执行代码，有文件大小限制。因此 Code 应产出摘要/索引文件（小体积 JSON/Markdown）push 到 main，Chat 读摘要而非原始大数据

## 分支管理

- **默认所有会话直接在 main 分支上提交和推送**（直推 main 政策，见 `memory/active/policy-direct-push-main.md`）
- feature 分支默认不用；但**守密人按任务派发可指定 feature 分支开发**（如 Web 环境强制建 PR / 特定流程，见 CLAUDE.md §7.6）
- 并行推送遇冲突时 `git pull` 后重试即可
- 如果未来有人工程序员加入，再考虑恢复分支保护

## 经验记录

### 会话替换问题
- **问题**：对话过期后，新会话需要从零了解项目
- **解决**：通过 CLAUDE.md + CONTEXT.md 体系，新会话 60 秒内进入工作状态

### 上下文污染问题
- **问题**：一个会话处理多个子项目时，上下文越来越乱
- **解决**：严格的职责隔离，一个会话一个子项目

### 知识易失问题
- **问题**：重要决策只存在于对话中，对话消失则决策丢失
- **解决**：所有决策立即写入 memory/decisions.md，git 永久保存

### 架构演进问题
- **问题**：早期决策（如"不使用框架"）随项目扩展不再适用
- **解决**：主控台定期审视架构，及时废除过时原则，记录在 decisions.md

### 分支管理问题（已通过废弃分支工作流解决）
- **问题**：多个会话各自开分支，时间久了分支散乱、架构不同步
- **旧方案**：定期由主控台整理分支，统一合并到 main 建立基线
- **最终方案**：全部直接推 main，废弃分支工作流。全 AI 团队不需要分支审查缓冲，AI 解决 git 冲突高效，分支+合并流程反而增加不必要的中转

### Issue 积压问题
- **问题**：战略参谋批量创建 Issue，Actions 执行失败后 Issue 悄无声息地积压
- **根因**：没有 WIP 限制、没有失败标记、没有去重检查
- **解决**：WIP 上限 3 个/子项目 + 失败自动打 blocked 标签 + 创建前查重

### 跨子项目资源归属问题
- **问题**：部署流水线、视觉规范等跨子项目关注点没有明确归属，导致 Code-wiki 和主控台各自创建了冲突的部署 workflow
- **解决**：新增 Code-site 子项目，专门负责主站、部署流水线和跨站视觉一致性

### 任务传递通道问题
- **问题**：Issue 只能传递给 GitHub Actions 自动触发的会话，手动开启的 Code 会话不会读 Issue
- **解决**：手动会话的任务入口是 CONTEXT.md「当前任务」段落，Issue 仅用于记录追踪

### 规则传播延迟问题
- **问题**：CLAUDE.md 规则变更后，已运行的会话仍按旧规则行事（如废弃分支后 Code-site 仍创建 feature 分支）
- **解决**：规则变更是非实时的，已运行的会话需要制作人手动告知。主控台变更应尽快推到 main，减少窗口期

### 主控台自主沉淀问题
- **问题**：主控台只在被提醒时才更新 memory 文件，不会主动沉淀决策和经验
- **解决**：明确为主控台核心职责——每个决策做出后、每次踩坑修复后，立即更新 decisions.md 和 lessons-learned.md，不等提醒

## 前台专岗分类与上下文管理

每个 chat 会话按职能分类命名，模拟专业分工：

**前台（Chat）角色：**
- 战略参谋 — 架构设计、文档交付、决策讨论
- 情报官 — 社区日报、舆情分析
- 数据员 — 数据库校验、JSON 补全
- 命轮审美 — 命轮卡面设计、美术方向

**中台（Code）角色：**
- 主控台 — 全局调度、跨子项目操作
- Code-news — 聚合器开发维护
- Code-wiki — Wiki 站点 + 数据库
- Code-game — 衍生游戏（待启动）

### 核心原理

每个 chat 的上下文窗口是有限的。如果所有话题混在一个 chat 里，上下文被稀释，前面的细节被压缩或丢失。按职能分类后，每个 chat 的整个上下文窗口只包含该领域的信息，形成专业纵深。

本质上是用 chat 分类模拟专业分工，用上下文窗口模拟专业记忆——每个 chat 就是一个专岗员工的大脑，只记得自己领域的事，但记得很深。

### 两轴记忆模型

- **横向（跨 chat 共享）**：GitHub 仓库 memory/ — 所有会话都能读取的结构化记忆
- **纵向（单 chat 纵深）**：上下文窗口 — 每个专岗 chat 自然积累的领域深度记忆

横向靠仓库，纵向靠 chat 分类。两者互补，缺一不可。

### 与 Project 功能的对比

Claude 的 Project 功能是给所有对话塞同一份背景文件，上下文是扁平的。专岗分类的做法是让每个 chat 自然积累各自领域的纵深上下文，仓库只负责跨 chat 的共享记忆。专岗分类在上下文利用效率上优于 Project。

## 战略参谋实战经验

### 派 Issue 的纪律

- **先问根因**：派 Issue 前先问——这个 Issue 是在解决真实问题，还是在补救上一个 Issue 造成的问题？后者说明应该先修上游。
- **机制优于一次性**：如果一个机制性 Issue（如自动分支清理）能让一个一次性 Issue（如手动分支清理）变得不必要，优先派机制性的，不要两个都派。
- **少派多盯**：战略参谋的价值在于结果质量，不在 Issue 数量。派出去的 Issue 要持续跟踪结果，而不是派完就忘。

### 交付物受众意识

- **先确认受众再动笔**：生成任何文档/报告前先确认受众——给制作人看、给团队看、还是给外部看，语言风格完全不同。
- **默认通俗**：默认用通俗语言，技术术语只在必要时出现。受众不是工程师时，尤其要避免专业黑话。

### 能力边界意识

- **承诺前先验证可行性**：不要承诺做不到的事。例如：服务器环境无法直接调用 B站 API（需要浏览器环境），不应列为可交付承诺。
- **验证后再对外说**：对外承诺的每一项能力，都应已经过本地验证或有可靠依据。

## 模型使用策略

| 角色 | 平台 | 模型 | 原因 |
|------|------|------|------|
| 教练/战略参谋/运营官 | Chat (MAX) | Opus Extended | 需要深度推理和判断 |
| 日常会话 | Chat (MAX) | Sonnet | 执行性任务，省额度 |
| 主控台 | Code 桌面 (MAX) | Opus | 全局协调需要强推理 |
| Code-wiki/news/site | Code 桌面 (MAX) | Sonnet | 执行性代码任务 |
| GitHub Actions | API | Sonnet | 成本最优，执行够用 |

原则：判断层 Opus，执行层 Sonnet。Extended Thinking 的价值在长链推理，翻译/格式化不需要开。1M context 当前用不上。

## AI 使用分级框架

| 级别 | 名称 | 人类角色 | AI 角色 | 核心跳跃 |
|------|------|---------|--------|----------|
| L0 | 无 AI | 做所有事 | 不存在 | — |
| L1 | 辅助应答 | 提问者 | 应答机器 | 开始使用 |
| L2 | 单任务委托 | 发包方 | 执行者 | 从问答到委托 |
| L3 | 多任务协作 | 实时搭档 | 协作伙伴 | 从孤立到关联 |
| L4 | 系统化运转 | 管理者 | 自主执行者 | 人从循环内到循环外 |
| L5 | 自演化系统 | 治理者 | 自我演化体 | AI 从执行到自主决策 |

Light 当前在 L3.5。L3→L4 是最难的跳跃，需要同时完成三件事：记忆外化（持久化）、判断编码（规则化）、调度自动化。

## 系统理论极限

1. **仓库认知承载量**：agent 上下文窗口有限，仓库文档膨胀后需要分层索引
2. **Issue 表达精度**：任务越复杂 Issue 歧义越大，复杂判断必须回到 Chat
3. **人类判断带宽**：通过"直觉编译成规则"持续上移，已编译的判断变成仓库的永久资产

## 伦理边界

核心体验内容绝不假手 AI——不是因为 AI 做不了，是因为这些东西一旦不由人来做，就失去了存在的意义，也是对用户期待的背叛。AI 做枯燥的机械工作和发现/洞察，人做需要感受和判断的创造。

## 银芯报告生产流程

社区情报报告（深度分析 / 职能建议 / 故障缺陷单 / 周报等）的可复用生产线，2026-05 沉淀。
完整 SOP 见命令 `.claude/commands/biav-report.md`（`/biav-report`），渲染引擎见 `scripts/report_render.py`。

六步骤：

1. **确认数据层**（§4 硬约束）：报告类一律走全量档案层 `Public-Info-Pool/Record/Community/`（2026-06-21 迁入，text 全量永驻 git），禁用输出层充全量（lesson #30）。
2. **单脚本提取**：写临时脚本（`/tmp/`）扫描 Discord（`Public-Info-Pool/Record/Community/discord/{区服}/channel_index.json` 映射 + `discord/{区服}/channels/{id_suffix}/{date}.jsonl`，区服 ∈ global/jp/volunteer（2026-07-10 方案甲），紧凑 schema 读取用 `.get(默认)`，见 CLAUDE.md §5.2）与 16+ 平台目录（与 discord 平级摊平于 `Record/Community/`，以 `ls` 为准）；保留原文+平台+日期+反应数。**不并行多脚本**（§6.11 R1）。
3. **甄别归纳**：标信度 A（硬事实）/ B（多源归纳）/ C（推断需标注）；区分官方确认 vs 玩家报告（R3）。`official-q-a` / `game-announcement` 是带状态标签的权威源。
4. **结构化 markdown**：经 `scripts/deliverable_path.py` 算路径落 `Public-Info-Pool/Resource/{主题类型}/{主题}-{YYYYMMDD}[-rN].md`（取代旧 `deliverables/{YYYY-MM}/`，月目录已废除），frontmatter（title/subtitle/basis/author/generated）+ `## 章节` + `◇ ◇ ◇` 分隔 + 加粗 label 条目。
5. **渲染**：`python scripts/report_render.py <md>`（依赖 `weasyprint`+`markdown`，ephemeral 容器需重装），自动从 frontmatter 出银芯视觉封面+目录+暗金主题 PDF/HTML；用 pymupdf 抽页核验。
6. **交付**：提交三件套 → 推送 → 建 PR（草稿）→ 汇报附 blob/PR/commit 超链接（§2.2 第5条）+ SendUserFile 直送 PDF。

经验：多语言关键词扫描噪声大（error↔terror、broken↔角色超模），命中后必须人工读原文剔噪；视觉引擎是这套流程唯一硬资产，必须固化在仓库而非 `/tmp`（容器回收即丢）。

## 防漂移：哨兵化标尺（守密人 2026-07-26 裁定四项落地后结晶）

本仓治漂移的主手法叫**哨兵**（sentinel）：把一条「靠人/AI 记得住」的对应关系，改成一条
「机器每次都查」的对应关系。`tests/test_claude_md_dates.py` 把它写在自己开头——
**「本哨兵把『同步』从承诺变成保障」**，这是全套手法的一句话纲领。

### 判据（一句话）

**它是否依赖某人在正确的时刻想起某件事？** 是 → 迟早漂移 → 该哨兵化。

CLAUDE.md §6.2 早写过同一句的另一个说法：「把弱约定（文档）升级为强约束（脚本）」。
lessons-learned 的毕业纪律写的是第三个说法：「文字劝告是弱约束，真防护在工具层」
（实证 #28/#34/#39 三记文字防不住复发、pre-push 钩子一次根治）。**同一条规律，三处独立发现。**

### 设计三戒（2026-07-26 三条实缝各贡献一戒）

1. **粒度要对齐事实，别对齐文件**。`memory_freshness.py` 管档案级 git 龄，而
   `project-status.md` 天天被别的子项目改、git 龄永远新鲜——SDK 那一节烂在里面 12 个发布无人喊。
   哨兵盯的必须是**那条具体的对应关系**（CHANGELOG 最新版本号 ↔ 状态节），不是承载它的文件。
2. **只钉机器判得了的，判不了的别硬钉**。机器能判「最新版本号有没有出现」，判不了「摘要写得好不好」；
   钉前者足以让 12 版落后当场翻红，钉后者只会制造噪音与豁免。**够用即止**是设计目标，不是妥协。
3. **前置步骤会掩盖产物的自洽性**。CI 永远先 build 再 test，于是「`npm test` 自己能不能跑」
   这个问题在 CI 里根本不存在。**凡是文档里写给人照抄的命令，都该有一条腿在干净环境里实跑**
   （`.github/workflows/family-cold-start.yml`）。
   本戒与上面的**「首跑实证纪律」是同一条规律的两端**——那条说「没跑过的机制，绿和坏长得
   一模一样」，本戒说「跑过了但被前置步骤兜着，绿同样不作数」。合起来读：**一个机制只有在
   它真实的起始条件下跑通过，才算存在**。

### 与「生成取代对账」的分工（招一 vs 哨兵，2026-07-26 同日两路落地）

同日另一路落了**招一·生成取代对账**（`scripts/build_status_facts.py` 把版本 / 规模 / 台账
条数生成进 `memory/project-status.md` 的 STATUS-FACTS 块）。**生成严格强于哨兵**——它让漂移
不可能发生，而哨兵只是发现漂移。故次序是：**能生成的先生成，生成不了的才架哨兵。**

生成不了的是哪一类：**叙述**。「当前版本是 0.76.0」可以生成；「0.75.0 做了 R7 会话末回写
可观测性、堵的是黑池进度卡静默变陈」不能生成——那是判断。而叙述层照样会烂：实证 2026-07-26，
`project-status.md` 顶部的机器块已正确写着 maestro 0.76.0，下方 maestro 叙述节**仍停在 0.69.0**，
生成块对它一无所知。`tests/test_status_doc_facts.py` 守的正是这一层（发布台账最新一版必须在
叙述里留下痕迹），与生成块不重叠。

**射程延伸（守密人 2026-07-26「3 推进」）**：哨兵原本要求「最新版本号出现在 CONTEXT.md
当前状态节」——那实质是**要求人手抄一个会变的数字**，与招一相抵。现已改为生成
（两包 `CONTEXT.md` 的 CONTEXT-FACTS 块：版本 / 发布日 / 锁步对端），哨兵同步收窄为只看叙述。
**这是「能生成的先生成」次序的一次实际执行：先扩生成层，再把哨兵让出那一维。**

### 生成层扩射程时的必查项：别把哨兵架空了（2026-07-26 实战教训）

把版本号生成进 CONTEXT.md 的**那一刻**，哨兵「版本号必须出现在当前状态节」就地变成永真——
生成块自己就带着那个号。**测试照常绿，守的东西却没了，而且它红不了，所以没人会发现它已经死了。**

这不是本次特有的坑，是生成层与检查层共存的通用失效模式。故立两条：

- **搜叙述前先剥生成块**（`_narrative()` 用 `<!-- X:BEGIN … X:END -->` 通配剥除，不是硬编码
  某个块名——下一个块不会再触发一次同样的事故）；
- **为「不架空」本身写一条非空控**（`test_narrative_stripping_is_not_vacuous`：构造一份版本号
  只存在于生成块里的档案，断言叙述检查仍判负）。哨兵的负控证明它会咬，这一条证明**它咬的
  还是原来那块肉**。

一句话纪律：**生成层每扩一次射程，回头点一遍现有哨兵的判据有没有被自己吃掉。**

### 两条配套纪律

- **空 allowlist 是目标**。豁免每条须写明理由，且必须是「经核实的哨兵已知盲区」而非「懒得改」。
  真实漂移应当 fail，由守密人裁「补回写」还是「加豁免」，而非默认吞掉。
- **新哨兵必须做负控**。「加了测试」不等于「测试会咬」——`tests/test_mutation_ratchet_matrix.py`
  撤腿转红、本轮四条负控（缺版本号 / 兄弟节不串 / 散文版本不冒充 / 节改名响亮失败）都是这个动作。
  没做负控的哨兵，与没有哨兵之间只差一次运气。
